# Agent Integration

<HostSupport hosts="desktop" />

Power Platform ToolBox can expose selected tools to AI assistants through its built-in MCP server. As a tool developer, you can decide whether your tool is discoverable by assistants, what input it accepts, what result it returns, and whether it supports only interactive runs or both interactive and automated runs. {{ className: 'lead' }}

## Overview {{ anchor: true }}

Agent integration builds on the same invocation model used for inter-tool workflows, but the caller is an external assistant instead of another PPTB tool.

At a high level, you need to do three things:

1. Declare an invocation contract.
2. Mark the tool as invokable by agents.
3. Add an automated runtime if you want the tool to work without opening its UI.

## MCP Contract {{ anchor: true }}

There are two distinct layers in the contract:

| Layer | Purpose |
| --- | --- |
| `invocation` | Describes the input payload the caller can send and the structured result the tool may return |
| `agents` | Declares that the tool is available to assistants and how it should behave when called through MCP |

The same `prefill` and `returnTopic` shapes used by PPTB invocation are also what assistants rely on for predictable tool calls.

## Interactive and Automated Runs {{ anchor: true }}

These docs use end-user language for the two execution styles:

| User-facing term | MCP runtime value | Meaning |
| --- | --- | --- |
| Interactive tool run | `executionMode: "windowed"` | PPTB opens the tool UI and the assistant works through the normal interactive experience |
| Automated tool run | `executionMode: "headless"` | PPTB runs the tool without opening the UI and returns a structured result when available |

Interactive runs are a good fit for existing UI-driven tools. Automated runs are a good fit for repeatable tasks, direct data returns, and unattended workflows.

When a tool supports both, the MCP server uses an **automated (headless) run by default** and falls back to an **interactive (windowed) run** when headless execution is not available.

## Declare Tool Metadata {{ anchor: true }}

Add both `invocation` and `agents` to `pptb.config.json`. See [Tool Configuration](/tool-development/pptb-config) for the complete field reference.

```json
{
  "invocation": {
    "version": "1.0.0",
    "capabilities": ["fetchxml"],
    "prefill": {
      "properties": {
        "entityName": {
          "type": "string",
          "title": "Table",
          "description": "Logical name of the table to build the query for",
          "required": true
        }
      }
    },
    "returnTopic": {
      "properties": {
        "fetchXml": { "type": "string" }
      }
    }
  },
  "agents": {
    "version": "1.0.0",
    "headless": true,
    "invokable": true,
    "modes": ["one-way", "two-way"],
    "defaultMode": "two-way",
    "timeoutMS": 12000,
    "executionModes": ["windowed", "headless"],
    "headlessEntry": "dist/headless.js"
  }
}
```

`agents` fields:

| Field | Required | Description |
| --- | --- | --- |
| `version` | **Yes** | Semantic version of the agent-facing contract. |
| `headless` | **Yes** | Whether the tool supports automated (headless) execution. Set to `false` for interactive-only tools. |
| `invokable` | No | Opt-in flag that exposes the tool through MCP discovery. |
| `modes` | No | Whether the tool supports fire-and-forget calls (`one-way`), result-returning calls (`two-way`), or both. |
| `defaultMode` | No | Fallback mode when the caller does not specify one. |
| `timeoutMS` | No | Timeout hint, in milliseconds, for result-returning calls. |
| `executionModes` | No | Supported execution modes (`windowed`, `headless`). When both are listed, `headless` is used by default and `windowed` is the fallback. |
| `defaultExecutionMode` | No | **Currently ignored** — headless is preferred whenever supported. May be removed in a future release. |
| `headlessEntry` | No | Path to the compiled automated runtime entry point. |

<Note type="warning">
  Don't use `defaultExecutionMode` to force interactive runs — it has no effect. For an interactive-only tool, set `"headless": false` and `"executionModes": ["windowed"]`.
</Note>

### Describe Input for Agents

Property descriptors in `invocation.prefill` support `title`, `description`, and `required` in addition to `type`, `enum`, and `items`. Agents use these fields to understand your input:

- `title` and `description` are shown to the user when the agent must ask for a value.
- `required: true` marks a value as mandatory. If the agent calls the tool without it, the value is requested from the user rather than guessed.

Add these fields to every input an assistant is likely to supply, especially required ones.

<Note type="important">
  In prose we refer to automated runs, but the runtime field value remains
  `executionMode: "headless"`. Use the real field names and values in your
  code and configuration.
</Note>

## Add an Automated Runtime {{ anchor: true }}

If you want your tool to support automated runs, export an `invokeHeadless(input, context)` function from a file that PPTB can discover.

PPTB checks for an automated entry in this order:

1. `agents.headlessEntry` in `pptb.config.json`
2. `dist/headless.js`
3. `headless.js`
4. `package.json.main`

This sample is based on the HTML sample tool and returns a simple FetchXML payload without opening the UI:

```javascript
/// <reference types="@pptb/types" />

async function invokeHeadless(input, context) {
  const { toolId, toolName, invocationMode, authToken, updateProgress, logger } =
    context

  logger.info(
    `Starting headless run for ${toolName} (${toolId}) in mode ${invocationMode}`,
  )
  updateProgress(10, 'validating input')

  const entityName =
    typeof input.entityName === 'string' && input.entityName.trim() !== ''
      ? input.entityName.trim()
      : 'account'

  if (authToken) {
    updateProgress(40, 'auth token received')
  } else {
    updateProgress(40, 'running without auth token')
  }

  updateProgress(80, 'building FetchXML')

  const fetchXml = `<fetch top="10">
  <entity name="${entityName}">
    <attribute name="name" />
    <attribute name="${entityName}id" />
    <order attribute="name" />
  </entity>
</fetch>`

  updateProgress(100, 'done')
  logger.info(`Headless run complete for entity: ${entityName}`)

  return { fetchXml }
}

module.exports = {
  invokeHeadless,
}
```

For two-way calls, return a JSON object that matches `invocation.returnTopic`.

## Report Progress and Logs {{ anchor: true }}

Automated runs can publish progress and runtime messages through the context passed to `invokeHeadless`. PPTB stores these updates with the job and displays them in the invocation detail view on the **MCP Server** page.

```javascript
async function invokeHeadless(input, context) {
  context.logger.debug('Received invocation input')
  context.logger.info('Starting data retrieval')
  context.updateProgress(25, 'loading records')

  try {
    const result = await loadRecords(input)

    context.updateProgress(100, 'done')
    context.logger.info(`Loaded ${result.records.length} records`)
    return result
  } catch (error) {
    context.logger.error('Data retrieval failed')
    throw error
  }
}
```

The logger supports `debug`, `info`, `warn`, and `error`. PPTB bounds the number of messages retained for each job, so logs are useful for diagnostics but should not be treated as permanent storage.

Keep messages concise and avoid logging access tokens, connection identifiers, complete input payloads, or sensitive result data. Throw an error when the invocation cannot complete; PPTB records the failure state and makes the error available in the invocation details.

## Invocation Metadata {{ anchor: true }}

Assistants can pass PPTB-specific metadata under `arguments.__pptb`.

```json
{
  "entityName": "account",
  "__pptb": {
    "mode": "two-way",
    "executionMode": "headless",
    "timeoutMs": 60000,
    "authToken": "optional-caller-token",
    "connectionName": "optional-saved-connection"
  }
}
```

Key fields:

- `mode`: `one-way` or `two-way`
- `executionMode`: `windowed` or `headless`
- `timeoutMs`: per-call timeout hint
- `authToken`: optional token provided by the caller
- `connectionName`: optional saved PPTB connection name

When your UI-based tool is launched through MCP, `toolboxAPI.invocation.getLaunchContext()` includes the original prefill data and a `__pptb` metadata object such as:

```json
{
  "entityName": "account",
  "__pptb": {
    "source": "mcp",
    "mode": "two-way",
    "correlationId": "mcp-...",
    "timeoutMs": 60000,
    "expectsResponse": true
  }
}
```

## Design for Both Run Styles {{ anchor: true }}

If your tool supports both interactive and automated runs, keep the contract aligned across both paths.

- Accept the same core input shape in the UI and automated runtime.
- Return the same result shape regardless of how the tool was executed.
- Treat automated runs as task-oriented operations, not hidden UI automation.
- Use progress updates and structured logging so callers can reason about long-running work.
- Keep secrets out of logs and return payloads.

The cleanest pattern is to move business logic into shared functions and have both the UI path and `invokeHeadless` call the same domain layer.

## Validation and Testing {{ anchor: true }}

Before publishing or sharing your tool with assistant users:

1. Validate `pptb.config.json` locally with [Local Validation](/tool-development/validation).
2. Check that the tool appears in MCP discovery only when `agents.invokable` is `true`.
3. Test both `one-way` and `two-way` calls if you advertise both modes.
4. Call the tool without each `required` prefill property and confirm the agent asks the user for it.
5. Confirm that your automated runtime returns a payload matching `returnTopic`.
6. Confirm that progress, runtime logs, results, and failures appear correctly in the PPTB MCP Server invocation details.
7. Use MCP Inspector as the manual test harness for tool discovery and tool calls.

To start MCP Inspector for debugging, run:

```bash
npx @modelcontextprotocol/inspector
```

If a call fails, compare the request and response payloads against `prefill` and `returnTopic`, then verify that the automated entry file can be discovered from your built output.
